# CLAUDE.md — 1inMINION: Heist to the Sun

## What this project is

A Next.js 14 (App Router) training website that teaches AI literacy to **non-technical
staff** through a gamified *Despicable Me* heist. Learners name their own Minion, then work
through four levels, each teaching one Claude capability they can use at work the next day.

- **Live:** https://1inminion.vercel.app/
- **Repo:** https://github.com/Vanshaj5101/Claude_1inMINION (public)
- Deploys automatically from `main` via Vercel. No backend, no database. One optional env
  var, `NEXT_PUBLIC_GA_ID` — see Analytics below.
- Package name is still `steal-the-sun`; the repo and folder are `Claude_1inMINION`.

## The four levels

| # | Title | Concept | What the learner does | Time |
|---|-------|---------|----------------------|------|
| 01 | Talk to Your Minion | Prompt Engineering | Runs a vague prompt, then builds a structured one one layer at a time | 15 min |
| 02 | Arm Your Minion | Projects | Builds a Claude Project, loads instructions + 374 records, proves the memory works | 25 min |
| 03 | Upgrade Your Minion | Skills | Asks for a deck, installs a Skill, asks for the identical thing again | 15 min |
| 04 | Give Minion the Wheel | MCPs | Connects Google Calendar, gives one goal instead of steps | 15 min |

**The single most important continuity rule — the chat chain.** Level 2 has the learner open
two chats (meet the Minion, then test the memory); the five mission questions and the special
tool happen in the *second* chat. Level 3 starts there, then **switches to a fresh chat**,
because a Skill only attaches to a conversation that starts after it is enabled — it cannot
join one already in progress, even when invoked by name with `/`. To avoid losing the
findings, Level 3 first asks the Minion for a mission brief in the old chat, which the
learner pastes into the new one. Level 4 then continues in that new chat.

So the chain is: **L2 chat → (brief handed across) → L3 chat → L4**. Any content change must
preserve it. This is also what makes Level 3's comparison fair: both runs work from the same
facts, so the Skill is the only variable.

Level 1 stands alone and needs no Claude Project.

## Architecture

**Content-driven levels.** Each level page reads its own `briefing.json` and
`resources.json` and renders them. Copy changes belong in `content/`, never in a component.

**No `steps.json`.** Earlier versions had one per level; nothing imported them and they were
deleted. Step lists now live as small arrays inside each level component (`buildSteps`,
`installSteps`, `connectSteps`) because they are tightly coupled to their screenshots.

**Checklist coupling.** Each level's `checked` boolean array must be the same length as its
`mission_check` array in the briefing JSON. Current counts: L1 = 8, L2 = 9, L3 = 4, L4 = 4.
Changing one without the other silently breaks the progress card and the mission check.

**Progress state.** `localStorage` only. `completedLevels` is written in exactly one place,
`MissionCheck.handleAdvance`, when the learner clicks the advance button. There is no UI to
reset it — use a private window to see the site as a first-time visitor.

**Minion name.** `PromptBlock` substitutes `[MINION NAME]` and prefixes `Hey NAME,` to every
copied prompt. `Level2Page` has its own `withMinion()` helper for the copy fields, which do
not go through `PromptBlock`.

## Conventions

- Edit copy in `content/`, not in components.
- Use CSS variables from `globals.css` (`var(--yellow)`, `var(--font-mono)`), not literals.
  `DESIGN.md` documents them.
- Level accents: 01 yellow, 02 purple, 03 blue, 04 orange.
- Mark-done controls go **bottom-right** of a card, never in the header.
- Tone: direct imperative, mission language, slightly dramatic. Never generic workshop
  phrasing. See `DESIGN.md` section 10.
- Match Claude's real UI vocabulary exactly — **Customize**, **Connectors**, **Instructions**,
  **Context**. Using near-miss words (for example "Project knowledge" instead of "Context")
  sends learners hunting for a screen that does not exist.

## Analytics

Two tools, deliberately. They answer different questions and neither needs a cookie banner
decision to be revisited.

**Vercel Web Analytics** — `<Analytics />` from `@vercel/analytics/next` in
`app/layout.tsx`. Cookieless, so visitor counts stay accurate without any consent
machinery. Only activates when deployed on Vercel; it is inert locally. Must also be
switched on once in the Vercel dashboard under the project's Analytics tab.

**GA4** — via `@next/third-parties`, gated on `NEXT_PUBLIC_GA_ID`. With no ID set nothing
renders and nothing is sent, so local dev is always clean. This is a plain cookie-based
install; Consent Mode was tried and removed, because denying storage broke the unique
visitor counts that were the whole point. Vercel Analytics covers that metric instead.

Custom events go through `trackEvent()` in `lib/analytics.ts`, which no-ops when GA is
absent so callers never guard. Currently `click_linkedin` and `click_portfolio`, fired from
the Connect menu. Pageviews (including client-side level navigation), outbound clicks, and
`.csv` downloads come free from GA4 enhanced measurement.

## Commands

```bash
npm run dev      # local dev
npm run build    # production build — the real check, run it before every commit
```

`npm run lint` is defined but **no ESLint config exists**, so it drops into an interactive
setup prompt. Use `npx tsc --noEmit` for type checking instead.
